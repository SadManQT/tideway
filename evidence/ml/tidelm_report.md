# TideLM evaluation (held-out test set)

300 planning and 200 extraction examples. Test examples use counterparty names never seen in training.
Base model: Qwen3-4B-Instruct-2507 (4-bit, MLX). TideLM: the same model plus Tideway's LoRA adapter (rank 16, 16 layers, 300 steps; validation loss 1.847 -> 0.020).

| Metric | Base model | TideLM |
|---|---|---|
| Valid JSON (plans) | 99.3% | **100.0%** |
| Intent accuracy | 12.7% | **100.0%** |
| Correct tools | 58.0% | **100.0%** |
| Exact plan (tools + every argument) | 27.3% | **97.7%** |
| Record precision | 0.916 | **0.993** |
| Record recall | 0.906 | **0.986** |
| Record F1 | 0.911 | **0.989** |
| Field accuracy | 77.2% | **98.5%** |
| Injection flag accuracy | 95.0% | **100.0%** |

Median latency per answer on an Apple M4 (16 GB): 2.8 s base, 4.87 s TideLM.

Exact-plan failures that remain are mostly a misspelt or dropped counterparty name, or a missed preference word. In the app these cannot cause harm: names are resolved against the ledger (an unknown name is refused, not guessed), only read/propose tools exist, and every number in the reply comes from Tideway's own tools.

Data is generated by tideway/ml/tidelm_data.py (synthetic, no real customer data). Reproduce with the commands in the README.
